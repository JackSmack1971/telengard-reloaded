## Requirements

- Add a low-clutter exploration HUD covering required survival/expedition
  information without exposing hidden danger/stat data.
- Provide keyboard/controller interaction for fight, defend, flee, feature
  interaction, required item/equipment actions, spell selection/quick-cast,
  map, and journal.
- Distinguish carried versus secured wealth.
- Communicate threat classification without exact hidden monster stats.
- Preserve known-versus-mysterious information rules.
- Use simulation commands for gameplay actions and presentation-only navigation
  for menus/focus.

## Non-Goals

- No work that delays TEL-129–TEL-132 solely to broaden optional MVP UI.
- No final UI art/typography asset production.
- No new gameplay verbs/formulas outside existing simulation contracts.
- No mouse-only required path.

## Invariants

UI actions do not directly mutate authoritative state. Hidden information remains
hidden. Presentation-only navigation leaves authoritative saves/state unchanged.

## Save Impact

None expected for presentation state. Any discovered missing authoritative
persistence must be assigned explicitly rather than stored in UI state.

## Tests / Observation

- Command mapping and authoritative-state checks for UI actions.
- Presentation-only navigation immutability checks.
- Keyboard and controller acceptance for required actions when TEL-125 resumes
  as post-MVP breadth.
- Fixed-seed Godot encounter/feature/inventory/spell/journal observation.
- Canonical full verification for code changes.

## Acceptance Criteria

After the Five-Floor MVP is proven, the first-slice Godot client can be played
through normal keyboard/controller UI for exploration, encounters, features,
items/equipment, spells, map, and journal without relying on debug commands or
presentation-owned gameplay state.

The Godot shell now enforces explicit interaction contexts and modal focus,

The ticket remains in progress. At this checkpoint the Godot host bootstrap

## Bootstrap and interaction update — 2026-08-24

The host now consumes the explicit development acceptance configuration at
`tools/Telengard.GodotHost/first-slice.config.json`. It supplies authored spell
and item IDs, non-zero player capacities, deterministic feature placements, and
encounter triggering through existing Core/content resolvers; it does not add a
save field or move authority into Godot. Feature interaction emits the existing
Core cues, and the client advances contact through qualitative threat
assessment before exposing combat actions.

The bootstrap boundary has a focused regression test. The doctor check,
Godot 4.7.2 headless/runtime checks, non-headless launch smoke check, and
canonical Full gate passed with 453 Release tests. The ticket remains in
progress because inventory still has no authoritative item-instance ownership
path for equip, and no recognized controller device was available for manual
controller acceptance. Bootstrap values remain application acceptance
configuration, not settled product tuning.

The item-instance ownership gap is explicitly outside TEL-113's completed
content-roster scope and has no existing owning ticket in the current ledger;
it requires a separately scoped TEL ticket before equip-from-inventory can be
implemented without inventing authoritative state here.

The subsequent interactive keyboard route exercised the live project with
Godot 4.7.2 on Windows: normal startup/inn/dungeon entry, map modal movement
isolation, fountain discovery/activation, attack, defend, flee, qualitative
threat presentation, and explicit selection/casting of the second known spell.
The host now completes Core contact/threat/enemy-turn transitions at the
application boundary, leaving Core as the legality and outcome authority.
Committed damage and feature outcome details are projected as safe cues. The
controller hardware criterion remains unverified because the environment
reports no recognized game-controller device.
