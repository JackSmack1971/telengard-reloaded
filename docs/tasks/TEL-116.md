# TEL-116 — Author the four first-slice dungeon feature definitions

## Status

Implemented and verified.

## Design Intent

Author exactly the four named first-slice dungeon features—fountain, altar,
pit, and teleporter—using the generic feature/outcome and knowledge contracts
already implemented in the simulation.

## Specification References

§9.3; §19–§25; §31; §34; §48; §51.

## Dependencies

- TEL-109 — content-pack and validation boundary.
- TEL-040 and TEL-041 — generic feature definitions and weighted outcomes.
- TEL-042–TEL-045 — existing fountain, altar, pit, and teleporter resolvers.
- TEL-050, TEL-051, TEL-055, and TEL-056 — knowledge/observation and
  teleporter-mapping contracts.

## Requirements

- Author exactly one valid definition for each of `Fountain`, `Altar`, `Pit`,
  and `Teleporter`; do not add a fifth first-slice feature definition.
- Provide stable IDs, interaction options, presentation keys, knowledge
  categories, and at least one selectable positive-weight outcome per feature.
- Use outcome conditions, effects, and observations supported by the existing
  generic/outcome and feature resolvers.
- Ensure the teleporter definition supplies only data needed by the existing
  teleporter mapping/activation contract; it must not implement mapping logic.
- Keep authored observations subject to the existing journal/knowledge
  qualification rules.

## Non-Goals

- No new feature type, resolver, activation command, teleporter algorithm,
  journal category, or renderer behavior.
- No permanent fountain/altar/pit/teleporter odds, damage, destination,
  resource, or balance rule where the specification is silent. Mark it
  `CONFIGURATION/TUNING DECISION REQUIRED`.
- No cubes, thrones, elevators, boxes, shrines, machines, or other features
  from the broader specification.

## Invariants

- Feature effects are resolved authoritatively by the existing simulation and
  feature resolvers after command validation.
- Hidden outcomes and unobserved feature facts do not become player knowledge
  merely because definitions are loaded.
- Feature placement remains valid dungeon geometry and renderer-independent.
- Weighted outcomes use stable content/version inputs and existing scoped RNG
  behavior where selection is random.

## Data Model / Content Boundary

Use `FeatureDefinition` and `FeatureOutcome` through TEL-109. Content supplies
data and identifiers only; `FountainResolver`, `AltarResolver`, `PitResolver`,
and `TeleporterResolver` remain the only feature behavior owners.

## Public API / Events

API classification: none for commands/events. Existing feature activation,
observation, and teleporter-mapping events remain unchanged.

## Determinism / Save Impact

Static feature loading has no RNG. Outcome selection continues through the
existing weighted engine and content-versioned scope. Save impact is none;
feature instances, knowledge, and mappings retain their current DTO contracts.

## Tests

- Validate exactly four first-slice definitions, one of each required type,
  with unique IDs and positive selectable outcome weights.
- Reject duplicate types/IDs, missing knowledge categories, malformed
  outcomes, unsupported effects, and invalid teleporter references.
- Activate one fixture for each feature through its existing resolver and
  assert committed events, observations, mapping, and state behavior remain
  renderer-independent.
- Prove loading alone does not mutate state or knowledge and repeated loads are
  deterministic.

## Acceptance Criteria

- The pack contains exactly fountain, altar, pit, and teleporter definitions,
  each with valid interactions, outcomes, and knowledge references.
- Existing generic feature and four resolver contracts consume the definitions
  without duplicated behavior or API/event changes.
- Invalid feature type, outcome, knowledge, and teleporter references are
  rejected by complete-pack validation.
- Focused activation, observation/mapping, hidden-information, and
  deterministic-load tests pass; unresolved tuning remains configurable.

## Definition of Done

The four feature files, complete-pack references, validation and resolver
fixtures, and documentation are complete; no new feature mechanics or
renderer logic is added. Production content loading, deterministic loading,
invalid-definition rejection, and resolver activation tests pass. Save impact
is none.
