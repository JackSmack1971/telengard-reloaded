## Status

Accepted. The floor-aware host composition is implemented, headlessly verified,
and observed through a complete Godot 4.7.2 five-floor traversal.

## Design intent

Replace the current hosted one-floor composition with a deterministic,
floor-aware session boundary that can legitimately traverse authored first-slice
floors 1–5 through the existing Core floor-transition rules.

## Current gap

The production-shaped Godot host currently retains one generated floor-1 layout
for dungeon entry/movement and does not expose the existing authoritative
`ChangeFloorCommand`/leave flow. Core already supports adjacent floor
transitions; this ticket composes that capability into the hosted client rather
than adding new dungeon rules.

## Requirements

- Provide a deterministic current-floor layout provider/cache for hosted play.
- Generate/reuse layouts from the authoritative world seed, generator version,
  and floor number.
- Resolve movement against the player's actual current floor layout.
- Expose normal client intent for using legitimate up/down stairs.
- Dispatch the existing Core floor-transition boundary with current and
  destination layouts.
- Support the existing floor-1 exit/leave boundary needed for retreat when
  reachable.
- Refresh renderer-safe projection/geometry after floor transitions.
- Preserve persistent map/fog behavior across revisited floors.
- Limit the MVP client path to floors 1–5 even though Core supports deeper
  dungeon positions.

## Non-goals

- No new dungeon-generation algorithm.
- No encounter-table composition; TEL-130 owns runtime ecology.
- No feature/loot integration; TEL-130 owns those paths.
- No save/resume; TEL-126 remains post-MVP.
- No final UI art or production assets.
- No renderer-owned stair legality.

## Invariants

Core remains authoritative for position, stair legality, expedition floor
history, and transition events. The Godot host/application may select the
appropriate generated layout for an authoritative command but may not mutate
`GameState` directly.

## Save/version impact

Expected none. This ticket composes existing deterministic generation and floor
transition state. Any newly discovered persisted-domain requirement must be
handled explicitly rather than stored as Godot scene state.

## Tests / observation

- Focused host tests for entering floor 1, descending, ascending, and moving on
  the destination layout.
- Deterministic repeated layout lookup for the same seed/version/floor.
- Revisit coverage proving previously known map state remains coherent.
- Boundary checks preventing accidental floor 6 traversal in the MVP client.
- Godot 4.7.2 interactive observation using real keyboard input traversed
  floor 1 → 2 → 3 → 4 → 5 and back to floor 1; continued movement was
  observed on destination floors.
- At floor 1 down stairs, `L` returned the authoritative frame to `scene=inn`
  while preserving floor 1 position `(60,49)`.
- Canonical full repository verification.

## Acceptance criteria

A hosted Godot session can enter floor 1, use legitimate stairs to traverse
adjacent first-slice floors through the existing authoritative transition
resolver, and continue movement/rendering on each destination floor without
Godot owning dungeon rules.
