# TEL-104 — Implement initial player setup and world-seed selection

## Status

Implemented and verified.

The new-game setup boundary now combines a supplied world seed, game mode, and
completed character result into a ready-at-inn authoritative state.

## Design Intent

Add the renderer-independent new-game setup boundary that selects a
deterministic world seed, creates the initial profile/game state, and places a
created character at the inn ready to enter an expedition.

## Specification References

§1.1; §5; §5.1; §28; §32.1; §36; §44; §48; §51.

## Dependencies

TEL-001, TEL-005, TEL-020, TEL-021, and TEL-100.

## Requirements

- Validate the requested game mode, character result, and world-seed input
  before committing setup.
- Persist the selected world seed and required version fields through the
  explicit profile/save contract.
- Initialize the player, inn boundary, empty expedition, knowledge/legacy,
  secured progress, and settings using existing state types.
- Make the resulting state ready for the existing dungeon-entry command.

## Non-Goals

- No character attribute generation (TEL-101–TEL-103).
- No seed generation algorithm beyond the supplied/selected stable input.
- No starting loadout, spell catalog, or content expansion.
- No renderer-specific setup flow.

## Invariants

The selected seed and version set are authoritative and stable. Setup is
atomic: invalid requests do not create partial profile or game state.

## Save Impact

This ticket owns profile/new-game persistence of the world seed and initial
setup fields. Use explicit DTOs, preserve version fields, and add migrations
for any persisted shape change.

## Tests

- Valid setup and seed round trip.
- Invalid mode/seed/character rejection without mutation.
- Ready-at-inn and enter-dungeon integration.
- Equal setup inputs reproduce equal authoritative state.

## Acceptance Criteria

A player can select a deterministic world seed and begin from a complete,
persistable initial state at the inn, ready for the expedition loop.

## Definition of Done

Focused implementation, headless/save tests, and documentation are complete;
no character-generation mode or content expansion is implemented here.

## Implementation Evidence

- Public API: `NewGameSetupRequest` accepts a caller-supplied stable seed,
  `GameMode`, and `CharacterCreationResult`; `NewGameSetupResolver.Create`
  validates the request and returns a committed `CommandResult`.
- State initialization: setup reuses `GameState.Create` for the selected seed,
  versions, mode, player identity, empty expedition, knowledge, legacy map,
  inn, secured progress, and settings, then applies the completed character.
- Validation and events: missing seeds, invalid modes, missing characters,
  dead characters, non-initial player state, null attributes, and invalid
  scalar state are rejected before a state/result is created; successful setup
  emits `NewGameCreatedEvent` with the committed identity, mode, and seed.
- Dungeon readiness: the resulting state round-trips through the existing save
  DTO and enters a generated floor-1 dungeon through `EnterDungeonCommand`.
- Determinism: equal seed, version, mode, and character inputs produce equal
  state and event results; no new RNG or seed-generation policy was added.
- Save impact: none; world seed, versions, mode, player, and initial state
  fields already use the explicit save DTO and save version 14 remains current.
- Tests: `NewGameSetupTests` covers valid initialization, invalid input
  rejection, deterministic replay, save round trip, event output, and dungeon
  entry readiness.
- Follow-up: no starting loadout, seed-generation algorithm, renderer setup,
  or content expansion was added; those remain outside this slice.
