# TEL-119 — Generate audit status fields from the canonical ticket/exec-plan ledger

## Design Intent

Make audit remediation status have one authoritative machine-readable source:
the ticket/exec-plan ledger. Generate the status fields consumed by
`docs/AUDIT_REMEDIATION_PLAYBOOK.md` and `docs/gates/AUDIT-P0.md` from that
source, while preserving human-authored rationale and historical evidence.

This is documentation/process infrastructure only. It does not change
gameplay, simulation authority, save behavior, coverage scope, mutation scope,
or game APIs.

TEL-119 is fully decoupled from TEL-117. It must be implementable before,
after, or without TEL-117 landing and must not require TEL-117's working-tree
changes.

## Requirements

- Declare the ticket/exec-plan ledger the canonical source for audit packet
  status and verification metadata, including at minimum:
  - packet ID;
  - status;
  - severity and priority;
  - area and compatibility sensitivity;
  - verified commit or explicit unresolved state;
  - active/completed exec-plan location where applicable.
- Define one deterministic, repository-local input format and precedence rule
  when a ticket and its exec plan both carry status metadata.
- Generate the corresponding machine-readable status fields in
  `docs/AUDIT_REMEDIATION_PLAYBOOK.md`.
- Generate the current-status/provenance section of
  `docs/gates/AUDIT-P0.md`, without rewriting the gate's historical baseline,
  verification date, acceptance evidence, or human-authored rationale.
- Mark generated sections explicitly with stable begin/end markers, for
  example:

  ```markdown
  <!-- BEGIN GENERATED: audit-status -->
  <!-- END GENERATED: audit-status -->
  ```

  The chosen markers must make manual edits inside generated sections
  detectable and must not overlap human-authored evidence sections.
- Preserve human-authored sections explicitly, including audit rationale,
  acceptance evidence, historical snapshots, and explanatory notes.
- Add a deterministic generator or equivalent checked-in rendering procedure
  whose output is reproducible for the same canonical ledger input.
- Add a stale-generation check to the repository workflow that regenerates or
  validates both documents and fails when the committed generated sections do
  not match the canonical ledger.
- Make the check reviewable and safe for pull requests: it must report the
  affected generated file/section and must not silently overwrite working-tree
  changes in CI.
- Document the source/derived-artifact relationship and the update command in
  the repository engineering documentation.

## Canonical-source decision

The ticket/exec-plan ledger is the canonical authority for current
machine-readable AUD-packet status. The playbook and P0 gate are derived views,
while `docs/BUILD_STATUS.md` remains append-only verification history.

When multiple records confirm completion, use the earliest current-`HEAD`
commit containing the implementation, regression tests, and contemporaneous
verification evidence as `verified_commit`. For aggregate historical claims,
use the first commit that makes the claim false and retain later packet commits
as supporting evidence. The generator must preserve this provenance rather than
selecting whichever document was edited most recently.

## Non-Goals

- No dependency on TEL-117 or changes to `eng/coverage.ps1` or
  `eng/mutation.ps1`.
- No gameplay, simulation, renderer, save DTO, migration, command, or event
  changes.
- No replacement of historical gate evidence with a newly generated summary.
- No automatic rewriting of human-authored rationale or verification prose.
- No broad documentation rewrite beyond source/derived-status instructions and
  the generated sections required by this ticket.
- No requirement to close or reopen audit packets; this ticket only makes the
  selected status source and projections consistent and checkable.

## Invariants

- A generated status field must have one traceable canonical input.
- Generated output is deterministic for identical ledger input.
- Historical baselines and verification evidence remain identifiable and
  unchanged outside marked generated sections.
- Stale generated output fails validation before merge.
- A clean checkout can regenerate the same output without TEL-117 changes.
- A reviewer can distinguish generated status from human-authored explanation
  without comparing multiple documents manually.

## Tests and Verification

- Run the generator twice from the same clean input and confirm byte-stable
  output.
- Change one canonical status field and confirm only the expected generated
  section changes.
- Edit or remove generated output and confirm the stale-generation check
  fails with an actionable message.
- Confirm human-authored sections remain unchanged by regeneration.
- Validate generated markers are present exactly once per generated section.
- Validate active/completed exec-plan references and commit provenance.
- Run the workflow validation in the same repository-local manner used by CI.
- Re-run the TEL-118 contradiction checks for AUD-001, AUD-002, AUD-005,
  AUD-007, and P1-remediation.
- Confirm the implementation and verification work on a clean checkout without
  TEL-117's uncommitted or committed changes.

## Acceptance Criteria

- The canonical ticket/exec-plan ledger and its precedence rules are named in
  repository documentation.
- Playbook and P0-gate generated sections are clearly marked and contain only
  derived status/provenance fields.
- Human-authored rationale and historical gate evidence remain outside the
  generated sections and survive regeneration unchanged.
- The generator produces deterministic output.
- The workflow stale-generation check fails on drift and passes when output is
  synchronized.
- All five TEL-118 contradiction checks pass against the generated views.
- TEL-119 has no dependency on TEL-117 and does not alter TEL-117 files.
- No unrelated documentation or runtime behavior is changed.

## Definition of Done

- Canonical source, field precedence, generated markers, and regeneration
  procedure are documented.
- Both derived documents are synchronized from the canonical ledger.
- Stale generated output is CI-detectable.
- Generated and human-authored content boundaries are reviewable.
- Determinism, preservation, and stale-output checks pass.
- The final diff is limited to TEL-119's ticket, source/derived-status
  infrastructure, workflow check, and required documentation.
