# TEL-013 — Implement tile visibility

## Design Intent
Deliver the specification-defined implement tile visibility slice while preserving Telengard's expedition loop, mystery, and renderer-independent simulation.

## Specification References
§7; §9–§12; §38; §43–§45.

## Dependencies
Prior related work: TEL-011, TEL-012.

## Requirements
- Implement only implement tile visibility and the integration points explicitly implied by the cited sections.
- Keep authoritative state and rules in the simulation; keep content definitions separate from simulation logic.
- Use the existing command/event boundary and preserve the documented product non-goals.
- Do not invent mechanics where the specification is intentionally silent. Mark any such choice CONFIGURATION/TUNING DECISION REQUIRED.

## Non-Goals
- No unrelated gameplay, presentation, refactor, or new TEL ticket.
- No permanent formula, balance, content catalog, or anti-save-scumming policy unless separately decided.
- No authoritative logic in scenes, UI components, sprites, renderer objects, or engine callbacks.

## Invariants
- Simulation validates state-changing commands before mutation.
- Presentation reads state and consumes events; it does not directly mutate authoritative GameState.
- Deterministic replay, scoped RNG, hidden-information, wealth, knowledge, and version invariants remain true where applicable.
- Undefined formulas and balancing remain CONFIGURATION/TUNING DECISION REQUIRED.

## Data Model
Use the smallest domain types required by the named specification sections. Keep runtime state separate from explicit save DTOs, and keep player-observed knowledge separate from hidden definitions.

## Public API
Expose only the smallest command, resolver, state, event, content, or DTO surface needed by this ticket. Do not silently redesign an existing public interface.

## Commands
Consume or add only commands required by this slice. Validate commands inside the simulation; presentation adapters may only create them.

## Events
Emit committed domain facts after successful authoritative transitions. Payloads must be stable and must not reveal unobserved hidden information.

## Determinism
Use stable inputs and scoped deterministic RNG streams wherever randomness exists. The same seed, versions, initial state, and command sequence must reproduce the same authoritative result.

## Save Impact
Assess profile and suspend save impact. Preserve save_version, simulation_version, generator_version, and content_version; add an explicit migration when persisted state changes.

## Tests
- Unit tests for valid, invalid, boundary, invariant, and event behavior.
- Determinism/replay tests for stateful or random behavior.
- Property tests for generation, invariants, or serialization where applicable.
- Headless tests for simulation behavior; graphical presentation is not required.

## Acceptance Criteria
- The behavior named by this ticket works through the simulation boundary.
- Relevant state, events, visibility, save, and deterministic replay checks pass.
- No undefined formula or balance rule was silently made permanent.

## Definition of Done
- Focused implementation, tests, and documentation are complete.
- Cited invariants remain true.
- The smallest relevant automated check passes.
- No gameplay outside this ticket is implemented.
