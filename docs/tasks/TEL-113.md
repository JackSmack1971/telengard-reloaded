# TEL-113 — Author the first-slice item roster

## Status

Not started.

## Design Intent

Author 10–15 item definitions for the first vertical slice using the existing
item template schema and the TEL-109 pack boundary.

## Specification References

§9.5; §29; §34; §36; §40–§42; §48; §51.

## Dependencies

- TEL-109 — content-pack and reference-validation boundary.
- TEL-060–TEL-065 — item category, instance, identification, affix, curse,
  and equipment contracts.

## Requirements

- Author between 10 and 15 unique item definitions, inclusive.
- Use the existing category, base-property, unidentified-name,
  identification, affix, curse, rarity, and depth-rule fields as applicable.
- Keep item IDs stable and ensure all affix/curse references use existing
  item-resolution contracts.
- Provide enough category and property diversity for the representative slice;
  do not inflate the count with duplicate definitions.
- Keep item-instance creation, identification, equipment, and treasure
  resolution in their existing runtime boundaries.

## Non-Goals

- No new item categories, affix/curse algorithms, equipment rules, inventory
  ownership model, or treasure-resolution behavior.
- No permanent item values, rarity rates, depth scaling, curse frequency, or
  loss policy where the specification is silent. Mark such values
  `CONFIGURATION/TUNING DECISION REQUIRED`.
- No content outside the first-slice count.

## Invariants

- Definitions are content, not item instances or authoritative inventory
  state.
- Unidentified/hidden properties remain hidden until the existing
  identification contract permits observation.
- Acquired items remain subject to the existing carried/unsecured wealth and
  treasure boundaries.

## Data Model / Content Boundary

Use `ItemDefinition` and its existing nested property/rule types, loaded via
TEL-109. Do not serialize runtime `ItemInstance` objects as content.

## Public API / Events

API classification: none for commands/events. Authored item records do not
change item, equipment, treasure, or journal event contracts.

## Determinism / Save Impact

Static item loading has no RNG. Affix/curse/loot selection continues using
the existing content-versioned scoped streams. Save impact is none.

## Tests

- Validate the inclusive 10–15 count, unique IDs, required fields, and
  canonical load order.
- Validate category/property/rule shapes and references in a complete pack.
- Prove unidentified names and hidden properties are not added to player
  knowledge by loading the roster.
- Exercise one representative item through existing instance/identification
  and save round-trip fixtures without changing those mechanics.

## Acceptance Criteria

- The first-slice pack contains 10–15 valid, uniquely identified item
  definitions using the existing item schema.
- The roster demonstrates meaningful category/property/identification/affix/
  curse/depth-rule coverage without duplicate stat-only variants.
- Existing item-instance, identification, and treasure boundaries consume the
  definitions without API or save changes.
- Focused roster, hidden-information, and deterministic-load tests pass.

## Definition of Done

The item files, complete-pack references, focused tests, and documentation are
complete; no inventory, equipment, treasure, or item-balance system is added.
