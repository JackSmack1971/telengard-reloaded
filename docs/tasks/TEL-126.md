# TEL-126 — Integrate Godot save, suspend, resume, and session lifecycle

## Status

Not started. **Post-MVP work.** Do not select this ticket until TEL-132 / the
Five-Floor MVP Demo gate passes, unless persistence becomes a demonstrated hard
blocker for the MVP itself.

## Design Intent

Expose the existing explicit persistence and expedition-suspension boundaries
through the playable Godot application so a real client session can be stopped,
resumed, loaded, and continued without renderer-specific authoritative state.

## Specification References

§6; §32–§33; §36; §42; §47–§48; §51.

## Dependencies

TEL-122, TEL-125, TEL-132, and the existing save/suspension implementation.

TEL-132 is an intentional sequencing dependency: the project first proves the
narrow five-floor MVP, then adds persistence breadth.

## Required Blueprint Context

- `docs/MVP_DEMO.md`
- `docs/presentation/GODOT_CLIENT_BLUEPRINT.md`
- `docs/presentation/UX_INTERACTION_BLUEPRINT.md`
- `docs/gates/GODOT-PLAYABLE-SLICE.md`

## Requirements

- Provide client flows for save/suspend, load/resume, and relevant error states.
- Use explicit save DTO/migration/application boundaries already owned by the
  repository.
- Rebuild presentation from loaded authoritative state rather than serializing
  Godot scene objects as gameplay state.
- Preserve deterministic continuation across save/resume for a fixed-seed
  scenario.
- Surface unsupported/corrupt save failures without partial GameState mutation.

## Non-Goals

- No work that pre-empts TEL-129–TEL-132 merely to broaden the client before the
  MVP is demonstrably playable.
- No new anti-save-scumming policy.
- No renderer-specific authoritative save format.
- No cloud/profile service work unless separately ticketed.

## Invariants

Save/load preserves authoritative state and version contracts. Godot transient
scene/animation state is not required for gameplay correctness after resume.

## Save Impact

Expected none if existing save contracts are sufficient. Any required
persisted-domain change must use an explicit DTO/migration/version decision and
be documented/tested in this ticket or reassigned if it exceeds scope.

## Tests / Observation

- Fixed-seed uninterrupted versus Godot save/resume authoritative comparison.
- Invalid/corrupt/unsupported save-path checks as applicable.
- Verify presentation rebuild after load.
- Manual Godot save/suspend/resume flow.
- Canonical full verification for code changes.

## Acceptance Criteria

After the Five-Floor MVP exists, a player can suspend/save and later load/resume
the first-slice Godot session, recover the same authoritative gameplay state
through the explicit save system, and continue play without relying on
serialized Godot scene state.
