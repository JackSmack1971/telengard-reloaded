# TEL-109 — Establish the data-driven vertical-slice content pack

## Status

Not started.

## Design Intent

Establish one external, versioned content-pack boundary for the recommended
first vertical slice. The pack must load the existing `Telengard.Content`
definition types without moving authoritative rules into content files or
presentation code.

## Specification References

§9.2–§9.6; §10.1; §33–§34; §42; §48; §51.

## Dependencies

- TEL-005 — existing explicit save/version contract, including
  `content_version`.
- TEL-030 — monster definition schema.
- TEL-040 and TEL-041 — generic feature and weighted-outcome contracts.
- TEL-060 — item definition schema.
- TEL-072 — spell definition schema.

TEL-110–TEL-116 depend on this pack boundary. Their authored identifiers and
cross-file references must not bypass the catalog/loader introduced here.

## Requirements

- Choose and document one repository-supported external format and directory
  contract for the pack under `content/`.
- Define a manifest containing the pack identity and stable `content_version`,
  plus the catalogs included in the pack.
- Load the existing monster, item, spell, feature, and loot definitions into a
  renderer-independent, read-only catalog. Provide the minimal extension
  points needed for bands and encounter tables; do not implement their
  gameplay resolution here.
- Validate required fields, unique identifiers, duplicate records, supported
  definition kinds, and all references that can be checked from a complete
  pack before returning a catalog. Reject invalid packs without exposing a
  partially loaded catalog.
- Define stable ordering/canonicalization rules so equal pack files and
  `content_version` produce equal catalog contents and deterministic consumers
  can use the catalog safely.
- Make the loaded `content_version` available to the existing version set;
  never silently substitute a different pack for a save that names an
  unavailable content version.

## Non-Goals

- No first-slice roster, band, encounter, loot, spell, or feature data beyond
  the smallest loader fixture needed to prove the boundary.
- No new monster, item, spell, feature, encounter, or loot mechanics.
- No renderer/UI behavior, presentation keys with authoritative meaning, or
  content-owned command/event resolution.
- No save-schema change. Existing saves already persist `content_version`.
- No permanent balance, weight, drop-rate, damage, cost, or outcome policy.

## Invariants

- Content definitions remain separate from authoritative simulation logic.
- Loading content does not mutate `GameState` and does not reveal hidden
  definitions through player knowledge or presentation state.
- Stable pack/version inputs remain available to deterministic systems.
- Invalid content is rejected before a simulation can consume it.

## Data Model / Content Boundary

The catalog may expose typed read-only collections for the existing
`MonsterDefinition`, `ItemDefinition`, `SpellDefinition`, `FeatureDefinition`,
and `LootTable` shapes, plus the minimal typed band/encounter records required
by TEL-110 and TEL-112. Runtime instances and resolver state remain in their
existing Core/Content boundaries.

## Public API / Events

API classification: additive. Add only the catalog, manifest, loader, and
validation result/exception surface required by this ticket; do not alter
existing commands or domain events. No domain events are emitted for loading
content.

## Determinism / Save Impact

Catalog ordering, identifier comparison, and reference resolution must be
stable and independent of filesystem enumeration order. Static loading has no
RNG. Save impact is none: `save_version` and DTO shapes remain unchanged, and
the existing `GameVersions.ContentVersion` remains the compatibility key.

## Tests

- Load a minimal valid pack and assert every catalog is read-only and stable.
- Reject malformed files, duplicate IDs, unsupported kinds, missing required
  fields, and invalid cross-references before returning a catalog.
- Prove filesystem ordering does not change catalog ordering or serialized
  catalog identity.
- Prove the manifest `content_version` is surfaced and an unavailable version
  cannot silently fall back.
- Prove loading leaves authoritative simulation state and knowledge unchanged.

## Acceptance Criteria

- A documented pack format and manifest can load through one
  renderer-independent catalog boundary.
- The loader validates complete-pack identity, uniqueness, schema shape, and
  resolvable references before returning a usable catalog.
- The catalog exposes stable typed definitions for the existing content
  schemas and reserved band/encounter data needed by TEL-110 and TEL-112.
- `content_version` is explicit, stable, and compatible with the existing save
  version contract; no save migration is introduced.
- The focused loader/validation tests pass and no gameplay rule is duplicated
  in the content layer.

## Definition of Done

The pack boundary, manifest/version contract, validation behavior, focused
tests, and documentation are complete. No first-slice content expansion is
claimed by this ticket.
