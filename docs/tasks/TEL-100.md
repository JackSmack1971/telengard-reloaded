# TEL-100 — Define character creation command boundary

## Status

Not started.

## Design Intent

Add the renderer-independent character creation contract that selects one of
the three specification-defined creation modes and produces a new player
record without embedding a mode's attribute-generation rules.

## Specification References

§5–§5.1; §26; §36; §51 ("A character can be created").

## Dependencies

TEL-001, TEL-003, and TEL-005.

## Requirements

- Add the smallest command/result boundary needed to request character
  creation and identify `ROLLED`, `POINT_ALLOCATION`, or `DAILY_SEED`.
- Validate the selected mode before any player or profile state changes.
- Keep mode-specific generation in TEL-101–TEL-103.
- Keep character state in the simulation and keep the boundary usable by all
  renderers.

## Non-Goals

- No rolled attribute formula or anti-reroll policy.
- No point budget or daily-calendar policy.
- No new-game seed selection, starting loadout, content catalog, or renderer.
- No change to the product specification.

## Invariants

- State-changing input is validated before mutation.
- A character creation result is deterministic for stable inputs and the
  selected mode/provider.
- No hidden definition data is exposed through the command or event surface.

## Data Model / API

Use the existing `PlayerState` and `GameState` shapes where possible. Add only
the creation mode/request/result types required to compose the three mode
implementations.

## Commands and Events

Add the smallest creation command and emit a committed character-created
event only after authoritative state is updated. Payloads must not include
unobserved generation inputs.

## Determinism and Save Impact

Mode providers must receive stable inputs; no process-global randomness or
clock may affect authoritative state. Assess profile-save impact and update
explicit DTOs/migrations if the persisted player shape changes.

## Tests

- Valid and invalid mode selection.
- Validation-before-mutation and committed event behavior.
- Stable repeated creation for equal inputs.
- Boundary and explicit save round-trip coverage if state changes.

## Acceptance Criteria

- The simulation accepts and validates the three named creation modes through
  one renderer-independent boundary.
- TEL-101–TEL-103 can implement their mode behavior without redesigning the
  command contract.
- No undefined formula or policy is made permanent.

## Definition of Done

Focused implementation, headless tests, and documentation are complete; the
smallest relevant automated check passes; no other gameplay is implemented.
