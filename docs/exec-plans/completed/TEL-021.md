# TEL-021 — Inn state

## Purpose / user-visible outcome

The simulation explicitly knows whether the player is at the inn. A new game
starts there, dungeon entry leaves the inn, and a valid return through the
existing dungeon-leave command reaches the inn.

## Scope and non-goals

Only TEL-021 landed: the inn state, its save DTO/migration, and the existing
entry/return integration points. Carried gold, secured gold, expedition
completion, rest, leveling, identification, loadouts, objectives, and
suspension remain later work.

## Current state

`GameState` now has `InnState`. `Enter` requires the player to be at the inn
and leaves it; `Leave` requires an active expedition at the floor-1 entrance
and reaches the inn. Save version 3 persists the state and migrates older
saves to the inn.

## Invariant impact

- State remains authoritative in Core and changes only through simulation
  resolvers.
- Entry and return validate before mutation; the existing committed dungeon
  event remains the return transition event.
- No randomness, hidden information, content, renderer, or wealth behavior is
  added.
- Expedition completion is intentionally not performed by TEL-021; a returned
  state remains active until the later completion transition.

## Save/version impact

The explicit save DTO now includes the inn state at schema version 3. Version 2
and version 1 saves migrate to `IsAtInn = true`. Simulation, generator, and
content versions are unchanged.
