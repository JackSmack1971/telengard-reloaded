# TEL-056 — Teleporter mapping

## Purpose / user-visible outcome

After observing a teleporter move, the simulation retains the observed source
and destination relationship. A first observation is `Observed`; a repeated
observation of the same relationship confirms it as `Mapped`.

## Scope and non-goals

Scope is TEL-056: teleporter-node content metadata, player-observed mapping
state, the simulation command/event boundary, teleporter integration, explicit
save DTOs, migration, and focused tests.

Out of scope: destination-rule semantics, network generation, random mapping,
balance, presentation, and all later TEL tickets.

## Current state

TEL-045 relocates through a configured destination and emits
`TeleporterOutcomeResolvedEvent`. Knowledge currently stores generic feature
observations, but no structured teleporter source/destination relationship.

## Invariant impact

- Mapping mutations remain simulation-owned and validate active/living state
  before producing a new immutable state.
- Only the observed source/destination pair is persisted; no hidden network or
  destination rule is copied into player knowledge.
- Teleporter integration uses the configured destination and adds mapping
  events only after relocation commits. No new randomness is introduced.
- Content metadata remains separate from runtime state and save DTOs.

## Save/version impact

The save schema advances by one version for the structured mapping collection.
Older saves migrate with an empty mapping collection; simulation, generator,
and content versions are preserved.

## Implementation plan

1. Add Core mapping state, command, resolver, and committed event.
2. Add the content-side teleporter node metadata and compose mapping into the
   existing configured teleporter resolver.
3. Persist mappings through explicit DTOs and migration, with round-trip and
   old-save coverage.
4. Update verified status/ledger documentation after the full gate.

## Decision log

- Model each observed source/destination relationship independently, keyed by
  network and node identifiers, so a configuration-defined destination rule can
  legitimately expose more than one observed relationship without overwriting
  prior knowledge.
- Confirm a relationship on a subsequent identical observation. This is the
  smallest state transition matching the specification's `OBSERVED` and
  `MAPPED` states; destination selection remains caller/content configuration.
