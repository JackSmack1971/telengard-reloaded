# TEL-101 — Rolled character creation

## Purpose / user-visible outcome

`ROLLED` character creation produces six observable starting attributes through
the existing renderer-independent character creation command boundary. Equal
world/version/player inputs and rolling configuration replay to the same player
state and committed event.

## Scope and non-goals

- In scope: `Telengard.Core` rolled provider, configurable attribute ranges,
  deterministic RNG stream usage, focused headless tests, and ticket evidence.
- Out of scope: point allocation, daily seed, starting loadout, derived stats,
  reroll limits, anti-reroll policy, and content expansion.

## Current state

TEL-100 provides `CharacterCreationResolver`, which validates the selected
mode, delegates to an injected `ICharacterCreationProvider`, commits the
returned `PlayerState`, and emits `CharacterCreatedEvent`. There is no rolled
provider; current tests use a recording test provider.

## Invariant impact

- Authority remains in the simulation provider and resolver.
- Validation and policy failures occur before the resolver returns a committed
  state or event.
- Attribute rolls use a named deterministic stream derived from world seed,
  simulation version, player identity, and policy version.
- The event exposes only player identity and mode; rolling policy and RNG input
  remain unobserved implementation inputs.
- No renderer or content boundary changes.

## Save/version impact

None. Generated attributes already exist in `PlayerState.Attributes` and are
covered by the existing explicit player/save DTOs. No save version or migration
changes are required.

## Public API / events

Additive: introduce the rolled configuration and provider types. Existing
`ICharacterCreationProvider`, `CharacterCreationRequest`, and
`CharacterCreatedEvent` contracts remain behavior-preserving and unchanged.

## Implementation plan

1. Add a validated six-range, versioned rolling configuration and `ROLLED`
   provider that draws one value per attribute from a named stream.
2. Preserve existing player fields while replacing only `Attributes`, then
   route through `CharacterCreationResolver`.
3. Add deterministic, boundary, event/state, hidden-input, and save round-trip
   tests.
4. Update ticket and append verified evidence after focused and full checks.

## Surprises / discoveries

- Direct execution of `./eng/dotnet.ps1` is blocked by the host PowerShell
  execution policy because the script is not digitally signed. A process-scoped
  `ExecutionPolicy Bypass` is required to invoke the repository wrapper; no
  repository or machine policy change is needed.
- Independent review identified that an arbitrary executable roll delegate and
  dungeon-generator-version coupling would weaken replay guarantees. The final
  implementation uses immutable six-range configuration data, an explicit
  policy version, and the simulation version as the RNG compatibility input.

## Decision log

- Use six caller-supplied inclusive attribute ranges plus a policy version
  rather than selecting a permanent dice formula or arbitrary executable
  policy. This satisfies the ticket while keeping authoritative randomness
  deterministic and leaving undefined balancing and anti-reroll decisions open.
- Keep the provider configuration outside persisted state. The resulting
  attributes are already the authoritative persisted output; RNG inputs are not
  exposed through the event contract.

## Results / remaining work

TEL-101 is complete. The six configured ranges are resolved through the
