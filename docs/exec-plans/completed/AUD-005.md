# AUD-005 — Unique deterministic expedition identity

## Purpose / user-visible outcome

Sequential expeditions for the same character receive distinct IDs even when
the simulation tick does not advance. Replaying the same command history, or
continuing after a save/load boundary, produces the same ordered IDs.

## Scope and non-goals

In scope: AUD-005, expedition identity state, its explicit save DTO and
migration, expedition/dead-hero tests, compatibility documentation, and the
required verification evidence.

Out of scope: AUD-001 and every other audit packet; changing dungeon layout
generation, encounter/content rules, death semantics, or unrelated cleanup.

## Current state

`DungeonWalkingResolver.Enter` hashes `WorldSeed`, `SimulationTick`, and
`Player.Id` only. `Leave` preserves no expedition counter, so a successful
expedition followed by a second entry at the same tick reuses the first ID.
The save contract currently ends at version 13 and persists the current
`ExpeditionId`, but not a count/nonce for prior expeditions.

## Invariant impact

- Simulation remains the authority for sequence advancement and ID creation.
- Entry validates and computes the next sequence before committing state/events.
- IDs remain deterministic and use no clock, process randomness, or machine
  input.
- Dead-hero records continue to capture the committed expedition ID.
- No hidden information, wealth semantics, content definitions, or renderer
  boundaries change.

## Save/version impact

Add an explicit `ExpeditionSequence` field to the root game-state save DTO and
advance the save schema from 13 to 14. A v13-or-earlier migration derives a
deterministic starting sequence: zero when no prior expedition ID is retained,
or one when the persisted current/last expedition has an ID. The latter makes
the next generated sequence two, so a completed expedition retained by an old
save is not silently assigned the same sequence on continuation.

Advance the current simulation compatibility version from 0.2 to 0.3 because
expedition IDs are event and encounter-scope inputs. Generator and content
versions remain 0.2 because dungeon generation and content definitions are
unchanged. Existing vectors are version-bounded; the new expedition-ID vector
is asserted explicitly.

## Decision log

- Store the monotonic sequence on `GameState`, not in a transient renderer or
  event, because entry and save/load need one authoritative lifetime value.
- Use the existing SHA-256-derived GUID scheme with invariant field formatting
  and append the sequence as an explicit ordered input; do not introduce a new
  RNG stream or alter dungeon generation.
- Migrate old saves with a retained expedition ID to sequence one, so the next
  entry advances to two; saves with no retained ID start at zero.
