# TEL-031 — Encounter trigger system

## Purpose / user-visible outcome

An active expedition can evaluate a deterministic encounter trigger at the
player's current dungeon position and emit a committed `EncounterStartedEvent`
when the configured trigger fires. The event carries a runtime monster
instance, while the simulation remains renderer-independent.

## Scope and non-goals

- In scope: trigger configuration, deterministic evaluation, monster-instance
  selection, encounter-start event, and movement integration when configuration
  is supplied.
- Out of scope: combat phases/actions, threat assessment, death, content
  catalogs, balance formulas, persistence, presentation, and TEL-032+.

## Sources of truth

- `docs/tasks/TEL-031.md`

- TEL-030 monster definition and instance types

## Current state

`MonsterDefinition` and `MonsterInstance` exist, but Core has no encounter
trigger resolver or encounter event. Movement emits only `PlayerMovedEvent` and
does not advance simulation time.

## Invariant impact

- Validation and event creation stay in Core; presentation only supplies
  commands/configuration.
- RNG uses a named stream scoped by expedition, simulation tick, and position.
- Event payload contains the observed encounter identity/position and runtime
  state, not the definition's hidden stats or resistances.
- Content remains outside Core; Core receives stable spawn options by ID.

## Save/version impact

None. No authoritative encounter state is retained by this ticket; combat
state belongs to TEL-032.

## Implementation plan

1. Add explicit trigger configuration/options and a Core resolver/event.
2. Integrate optional configured checks into movement without changing the
   existing no-configuration path.
3. Add valid, no-trigger, invalid, deterministic, event, and hidden-state
   tests; update verified status.

## Surprises / discoveries

The ticket and specification define the encounter lifecycle but do not define
trigger probability, candidate catalogs, or stat-scaling formulas.

## Decision log

- Keep the trigger stateless and do not add save fields before combat state
  exists; the supplied simulation tick and position provide stable scope.
- Require callers to provide chance and spawn options, avoiding invented
  content or balance values.

## Results / remaining work

TEL-031 is implemented and verified. The simulation evaluates configured
encounter chances with a scoped deterministic RNG, creates a runtime monster
instance from explicit spawn options, and emits `EncounterStartedEvent` after
movement. Combat state, content catalogs, balance, and persistence remain
intentionally deferred.
